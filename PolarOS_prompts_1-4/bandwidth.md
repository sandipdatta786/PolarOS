# PolarOS — sync bandwidth measurement

**This is a measurement, not a claim.** Every number below was produced by
`measure_bandwidth.py` reading `season.db`. Re-run it and the numbers
reproduce exactly; the generator is seeded and gzip's mtime is pinned.

Node measured: **MAITRI**, whole season. The winter-over (2027-03-01 to 2027-11-30) is called out
separately where it matters.
Days with traffic: **339** (of which 275 in the winter-over). Events: **1272**.

## 1. The link budget

| | |
|---|---|
| Link rate | 2400 bit/s (Iridium circuit-switched data) |
| Window | 900 s (15 min) |
| Theoretical capacity | 2400 x 900 = **2,160,000 bits** = **270,000 bytes** = 263.7 KiB |
| Usable at 60% goodput | **162,000 bytes** = 158.2 KiB |

The 60% figure is a deliberate haircut for modem negotiation, PPP framing
and TCP overhead. Quote the usable number, not the theoretical one — if a
judge asks why, this paragraph is the answer.

## 2. A representative day

The **median** day by event count, not the mean: the mean is pulled around by
the monthly audit days, and we wanted a day that actually happened.

| | Average day (2027-03-02) | Worst day (2026-12-28) |
|---|---:|---:|
| Events | 2 | 198 |
| Raw JSON | 437 B | 50,476 B |
| gzip -9 | **218 B** | **2,321 B** |
| Compression | 2.0x | 21.7x |
| Bytes/event (gzip) | 109 | 12 |
| Share of usable window | 0.13% | 1.43% |
| Airtime needed at 2400 bit/s | 1.2 s | 12.9 s |

### The arithmetic, longhand

```
average day: 2 events -> 437 B raw -> 218 B gzipped
  218 B x 8            = 1,744 bits to send
  1,744 bits / 2400 bit/s  = 0.7 s of airtime (theoretical)
  / 0.60 goodput      = 1.2 s of airtime (realistic)
  window is 900 s      -> margin 743.1x
```

## 3. Backlog — the case that actually matters

A station is not offline for a day. It is offline for a week of blizzard, or
a fortnight of antenna icing, and then it gets one window. So the real
question is how many days of accumulated log one window can drain.

We can answer it without a table. MAITRI's **entire log for the whole season**
— 1272 events across 339 days with traffic — compresses to **16,600 B**, which is
**10.2% of one usable window**. If the whole season fits, every possible
backlog fits, and there is no worst case left to find.

Note the compression effect: the 339 daily blobs sum to 86,567 B, but the same
events compressed as **one** blob are 16,600 B. Event logs are extremely
repetitive — the same 18 type strings, the same node ids, the same JSON keys,
over and over — so a backlog compresses far better than a single day does.
The system gets *more* efficient the longer it has been offline, which is
exactly the wrong way round from what people expect. Say that in Q&A.

## 3b. The heaviest node-day in the entire system

Across all five nodes and the whole season, the single busiest node-day is
**MAITRI on 2026-12-28** (198 events) — the day the ship offloads and a station records
a season's cargo in one shift. This is the worst case the design ever faces.

| | |
|---|---:|
| Events | 198 |
| Raw JSON | 50,476 B |
| gzip -9 | **2,321 B** |
| Share of usable window | **1.4%** |
| Airtime at 2400 bit/s | 12.9 s of a 900 s window |

This is the number to quote if a judge accuses the winter figures of being
easy. The busiest day the system will ever have still needs 13 seconds.

## 4. Priority drain

If a window were ever too small, priority 1 (safety) drains first.
The safety day that matters is **BHARATI on 2027-01-25**: the overdue field party and
everything it triggered — 3 priority-1 events (ALERT_RAISED, PARTY_OVERDUE, SOP_TRIGGERED).

That slice is **345 B gzipped**: 0.213% of the usable window, **1.9 seconds**
of airtime. Even on a link so degraded that only ten seconds of the window
survives, the safety traffic still gets through — which is the entire reason
`priority` is a column in the schema rather than a nice idea in the deck.

## 5. What this does and does not prove

**Proves:** the delta a node needs to send is small enough that bandwidth is
not the binding constraint on this design. The binding constraint is window
*availability*, not window *size*.

**Does not prove:** that a real Iridium link achieves 60% goodput, that the
session survives a 15-minute call without dropping, or that a production
wire format would serialise exactly like this JSON. Those need a real modem
and are honest 'not yet tested' answers in Q&A.
